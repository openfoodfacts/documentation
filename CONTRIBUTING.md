# Contributing to Open Food Facts documentation

Thank you for helping improve Open Food Facts documentation. Contributions can be code, documentation, examples, accessibility improvements, translations, issue reports, or reviews.

## Before you start

- Search the [issue tracker](https://github.com/openfoodfacts/documentation/issues) to avoid duplicate work.
- For a substantial change, open or comment on an issue before investing significant time.
- Keep each pull request focused on one problem.
- Never include secrets, private product data, or personal information.
- Follow the [Open Food Facts forum guidelines](https://forum.openfoodfacts.org/faq) and treat other contributors respectfully.

If you are unsure where a change belongs, open an issue or ask in the [Open Food Facts community Slack](https://slack.openfoodfacts.org/).

## Choose the correct source

Some documentation in this repository is synchronized or generated automatically. Editing generated output directly can cause a later workflow to overwrite the change.

| Change | Preferred source |
| --- | --- |
| Documentation-site UI, navigation, metadata, or build configuration | This repository |
| Product Opener developer and API source documentation | Usually [`openfoodfacts/openfoodfacts-server`](https://github.com/openfoodfacts/openfoodfacts-server); ask in an issue when uncertain |
| OpenAPI specifications under `ref/` and `specfiles-json/` | Generated or synchronized by the OpenAPI documentation workflow; do not hand-edit unless the task explicitly requires it |
| Generated API MDX under `content/docs/**/(api)/` | Generated by `npm run generate-docs`; change the source specification instead |
| Transpiled Product Opener material under `content/docs/Product-Opener/(docs)/` | Generated from Product Opener documentation; change the upstream source instead |

The workflows in `.github/workflows/` and `scripts/generate-docs.mjs` are the authoritative description of current synchronization and generation behavior.

## Local setup

The deployment workflow uses Node.js 20 and npm.

```bash
npm ci
npm run dev
```

Open <http://localhost:3000> to view the site.

## Make and validate a change

Create a branch in your fork, make the smallest change that solves the issue, then run the checks relevant to your work:

```bash
npm run format:check
npm run lint
npm run build
```

`npm run build` is the deployment-equivalent validation. Run `npm run generate-docs` only when the issue explicitly requires regenerated documentation, because it rewrites generated paths.

For prose changes:

- use clear, direct language and define uncommon terms;
- keep examples small and runnable;
- add useful alternative text to images;
- link to stable primary sources where possible;
- preserve the project's terminology and file organization;
- do not mix a broad generated-content refresh into a small manual edit.

## Open a pull request

In the pull request description, include:

- the problem and why the change helps;
- the files or documentation area affected;
- whether any content is generated or synchronized;
- the commands you ran and their results;
- screenshots when a visible interface changed;
- the related issue, using `Closes #123` only when the PR fully resolves it.

Maintainers may suggest a different source repository or ask for a smaller scope. That redirection protects generated documentation and is a normal part of review.

## Non-code contributions

You do not need to prepare code to help. Open a documentation issue with:

- the page URL or repository path;
- what is unclear, inaccurate, inaccessible, or missing;
- the expected behavior or suggested wording;
- a primary source or reproducible example when relevant.

This gives maintainers enough information to route and reproduce the problem.
